# 本地旧引擎 EEX 命令规格与验证

> 文件名为历史遗留；本文已不是待实现草案，而是当前本地旧引擎的
> 实证记录。可执行规格以 `eex_schema.py`、`parse_eex_to_ast.py` 和
> `write_eex_from_ast.py` 为准。

## 1. 适用范围与证据等级

本文只描述当前 `ccz/Ekd5.exe` 和 `eex_ccz/*.eex` 使用的旧引擎格式。

证据优先级如下：

1. 本地 117 个 EEX 文件的字节结构与受控回写结果；
2. 本地 `Ekd5.exe` 的命令分派、参数读取和执行调用；
3. 与原版/旧引擎同期的资料；
4. Star、新引擎及带版本号的扩展资料，仅用于识别版本差异，不用于给
   旧引擎字段定名。

## 2. 命令域边界

本地旧引擎命令分派器位于 `0x004109EF`：

- `0x004109FB`：读取一个 `u16le` opcode；
- `0x00410A0F`：与 `0x006B` 比较；
- `0x00410A13`：大于 `0x6B` 时跳到 `0x00411126`，返回错误码 5；
- `0x00410A1C`：以 `0x0041112F` 为 108 项跳转表分派
  `0x00..0x6B`。

因此：

- 旧引擎合法数值域为 `0x00..0x6B`；
- `0x6C` 以上不能作为本地旧引擎命令规格；
- 之前混入的 `0x6E..0x90` Star/新引擎占位项已从 schema 和写回器删除；
- 解析器和写回器现在都会明确拒绝超过 `0x6B` 的 opcode。

## 3. 本地语料覆盖

语料共 117 个文件：

- `R_00.eex..R_58.eex`：59 个；
- `S_00.eex..S_57.eex`：58 个。

全量解析结果：

- 117/117 成功；
- 实际出现的普通命令范围为 `0x03..0x6B`；
- `0x00` 是段终止/分隔标记，`0x01` 是子块，`0x02` 是内部消息；
- 语料未出现 `0x28`；
- 语料未出现任何 `>=0x6C` 命令。

数值域中 `0x00..0x6B` 的每一项都能由本地主程序分派，但“分派存在”不
等于“原版语料使用”。当前结构解析器覆盖除结构标记外的全部已知格式，
并依据主程序补上了原版语料未出现的 `0x28` 参数结构。

## 4. 字节保真验证

验证了两条独立闭环：

```text
EEX -> AST -> EEX
EEX -> AST -> DSL -> AST -> EEX
```

对 117 个文件，两条路径均为 117/117 **逐字节相同**，不是只比较 AST
或重新解析成功。

其中发现 22 条字符串不是 GBK 可编码字符，但全部可以按 GB18030
四字节序列无损往返。结论为：

- 文件中的常规汉字兼容 GBK；
- 安全的完整编码声明应为 GB18030；
- 写回器已由 GBK 改为 GB18030；
- AST 内仍保留 `*_raw`，直接 AST 回写时优先使用原始字节。

## 5. 三条旧引擎命令的本地调用结论

### 5.1 `0x10`

- 参数：无；
- 本地语料：仅 `S_00.eex` 一次，位于隐藏指导人物后、人物消失前；
- 解析函数：分派到 `0x0041590D`，再调用 `0x00433359`；
- 格式：已验证；
- `0x00433359` 依次调用固定教学段落，其中本地字符串明确包含
  “关于敌军和友军的解说”和“有关部队的操作”；
- 因此旧引擎语义定名为 `battle_operation_tutorial`（战斗操作教学）。

### 5.2 `0x28`

- 本地 117 个脚本未出现；
- 本地主程序 `0x00414361` 明确读取参数标记 `0x0036`；
- 随后读取一个 `u16le`，保存到命令对象；
- 二进制结构为：

```text
28 00 36 00 vv vv
```

- 解析器、schema 和写回器已按此结构实现；
- `0x00414361` 调用 `0x00418518`，只把参数写入脚本对象 `+0x203C`；
- 对应 getter `0x00418531` 在本地程序中没有调用点，字段也没有其他
  直接访问路径；
- 原版语料又完全不使用该指令，因此按旧引擎的实际效果定名为
  `set_reserved_script_value`，字段名为 `reserved_value`，明确表示
  它是写入后不消费的保留值。

### 5.3 `0x6A`

- 参数：无；
- 原版语料出现 3 次；
- 处理函数 `0x00416DFA` 只在战场模式执行，并清零
  `0x004B3D10`；
- 该全局量是 `0x5B`“高亮区域”矩形绘制路径的启用标志，相关坐标位于
  `0x004B3D14..0x004B3D17`；
- 三处原版脚本也都位于胜利条件显示后的高亮切换位置，因此定名为
  `clear_highlight_area`（清除高亮区域）。

轩辕春秋 2007 年“新曹操传引擎发布”明确写的是：过去未知的 `0x28`
和 `0x6A` 在**新引擎中更改为**“自由 R 开关”和“Game Over”。这恰好
证明这些名称不能倒推本地旧引擎。本项目的定名只来自上述本地机器码和
原版脚本上下文。

### 5.4 `0x37` / `0x3A` 全局量运算

本地 `Ekd5.exe` 的命令跳转表把 `0x37` 分派到 `0x004118D4`，
把 `0x3A` 分派到 `0x004149F7`。机器码可直接确认：

- `0x37.operator2 = 0`：当前值 `>= value`；
- `0x37.operator2 = 1`：当前值 `< value`；
- 其他值：当前值 `== value`；
- `0x3A` 的类型 0 与类型 2：`operator = 0/1/2` 分别为赋值、增加、
  减少；
- 类型 0 上限为 `999999`，类型 2 上限为 `100`，减少不会低于 0。

类型 0 的修改函数位于 `0x0040E1A0/0x0040DBED/0x0040DC23`；类型 2
的修改路径位于 `0x00418D00/0x0040D2A9/0x0040D3AE`。原版语料中
`0x37` 只使用类型 0、2，`0x3A` 也只使用这两类。

预览 VM 已实现这一机器码核实子集。由于类型 0/2 的进入事件初值来自
游戏运行态，用户未提供初值且脚本此前没有赋值时，条件仍标记为未知，
不会默认当作 0。

## 6. 命令规格状态的含义

`eex_schema.py` 的 `status` 描述语义定名程度，不描述能否无损读写：

- `done`：参数结构与主要运行语义均已定名；
- `partial`：只用于 `0x00` 事件段分界和 `0x03` 否则分支两个结构控制
  标记；它们的字节和控制作用已知，但不是可孤立解释的普通执行命令；
- `placeholder`：无参数结构已知，名称主要来自旧编辑器/上下文，尚缺
  足够本地执行证据。当前本地旧引擎的 `0x00..0x6B` 表中已无此状态。

无论 `status` 为何，本地实际出现的命令都已经通过逐字节回写验证。
完整字段顺序不在本文复制第二份易失真的 Python 表，而直接以
`eex_schema.py` 为单一可执行来源；中文总表和主要命令字节布局见
`EEX二进制格式说明.md`。

## 7. 编辑器安全规则

- 不允许把 `unknown_XX` 或 `cmd_XX` 形式绕过旧引擎上限；
- 不支持的域内 opcode 在写入 opcode 之前即报错，避免留下半截输出；
- `0x00`、`0x01`、`0x02` 分别由 Section/ChildBlock/Comment 结构处理；
- 对保留布尔值仍保留原始两字节，可区分
  `0000`、`0100`、`ff00`、`ffff`；
- Star/新引擎扩展命令应放入独立版本模块，不能重新混入
  `COMMAND_SPECS`。

## 8. 可复现命令

```bash
./venv/bin/python dsl_eex_roundtrip_check.py eex_ccz/*.eex
```

该命令应输出 117 行 `OK bytes-identical` 并以状态码 0 结束。
